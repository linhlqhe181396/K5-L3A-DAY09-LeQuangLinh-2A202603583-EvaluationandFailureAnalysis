# PRD v1.1 — LogiX-VN refund agent (evaluation and release criteria)

> v1.1 does not change refund functionality. It makes “runs correctly” measurable and adds a
> pre-merge gate. Results below are generated by the harness; run IDs identify the evidence.

## 1. Changes from v1.0

| Area | v1.0 | v1.1 |
|---|---|---|
| Success criterion | “The agent handles refund requests correctly” | Metric thresholds and paired-regression checks in `config/metric_spec.yaml` |
| Evidence | Manual demo | Report with run ID, eval-set SHA, and gate output |
| Risk | General risk list | Failure taxonomy FM-01–FM-09 with code graders |

## 2. Pilot scope

- **In scope:** one public claim and its owner’s order; eligible, denied, expired-approval, and
  previously-refunded cases represented in the public fixture; deterministic MockLLM evaluation.
- **Out of scope:** production users, real payments, legal disputes, and behavior of a live LLM.
- **Measurement environment:** MockLLM; v1 has 14 items × 5 seeds. v2 adds 14 adversarial claims
  (28 items total) without changing the Lab 8 implementation.

## 4. Failure mode → grader

| FM | Failure | Grader | Method | Rationale |
|---|---|---|---|---|
| FM-01 | Secret leak | `SecretLeak` | Code | Compare forbidden secrets with trace/artifact text. |
| FM-02 | Ignore denial | `TrialPass`, `ApprovalBypass` | Code | Status and authorization are structured facts. |
| FM-03 | Trust ticket over DB | `DbFactKept`, `TrialPass` | Code | Detect override events and wrong outcomes. |
| FM-04 | Sum/rounding error | `ProposalAmountCorrect`, `RefundAmountCorrect` | Code | Exact VND amounts are deterministic. |
| FM-05 | Prior refund / pre-deduction error | `ProposalAmountCorrect`, `RefundAmountCorrect` | Code | Compare proposal and committed ledger amount to labels. |
| FM-06 | Stale policy clause | `TrialPass` | Code | Current clause and outcome are structured. |
| FM-07 | Sibling-claim refund | Ledger checks, `TrialPass` | Code | Claim identity, refund rows, and caps are structured. |
| FM-08 | Reply/ledger mismatch | `ReplyMatchesLedger` | Code | Parse the reported amount and compare to the committed ledger. |
| FM-09 | Cross-principal access | `TrialPass`, `SecretLeak` | Code | Authorization and protected fields are structured. |

Judge calibration is a separate advisory check: tone replay meets the numeric floors, but
helpfulness does not. No judge is used for money or approval decisions.

## 5. Release gate

- **Command:** `python -m lab9.gate --pr reports/eval_<shape>.json --baseline reports/baseline_v1.json`
- **Baseline owner:** evaluation owner on the protected branch; baseline is generated, not edited.
- **Compatibility:** PR and baseline must have the same eval-set SHA and complete item × seed rows.
- Generated reports carry the metric spec used for evaluation. The gate checks it against the PR
  spec and compares it with the baseline-embedded spec to enforce the same-version ratchet.
- **Exit 1:** do not merge. The evaluation owner reviews the first failing trace, fixes or rejects
  the change, then reruns evaluation. Any waiver must be approved by the product owner and
  recorded in the PR with rationale and expiry.
- The `eval-gate` workflow checks the current swarm, fixed, and seeded-regression controls.

## 6. Missing evidence and open risks

- [ ] No real-user data; MockLLM does not represent live model behavior.
- [ ] Fourteen v1 items give limited power; confidence intervals can be wide.
- [ ] Judge audit is replayed on public labels, not a held-out human sample.
- [ ] A 1-in-3-seed bug cannot be detected reliably with only five seeds; increase repetitions or
  use targeted tests rather than weakening a threshold.
- [ ] `reply_ledger_consistent` is applicable only when the trace contains a reply event; the
  reference swarm does not record one, so that metric cannot assess its missing reply evidence.

## 7. When to publish v1.2

- Add cases or change labels: increment `eval_set_version`, regenerate labels, and create a new
  baseline.
- Change metrics or thresholds: increment `metric_spec_version`, document the rationale, and
  ratchet thresholds only in the stricter direction for an unchanged eval-set version.
